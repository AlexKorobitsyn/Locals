# Музыкальный сервис

Девять уровней XP, предложения сообщества без порога входа, голосование,
подтверждённые организаторы и админка: [инструкция](docs/EXPERIENCE.md).
Карта площадок, событий и выбор места при добавлении: [инструкция](docs/MAP.md).

Основа приложения: Python 3.12, FastAPI, Pydantic v2, async SQLAlchemy 2.0 и
PostgreSQL 16. Прикладные маршруты и документация доступны под `/api/v1`.

## Запуск через Docker Compose

Создай `.env` по образцу `.env.example`. В уже существующем `.env` добавь
недостающие переменные, включая `COMPOSE_PROFILES=local` для локальных PostgreSQL
и MinIO. `POSTGRES_PASSWORD` и пароль в `DATABASE_URL` должны
совпадать; специальные символы в URL нужно кодировать. Внутри compose БД доступна
по имени `db`. `.env` исключён из Git и контекста сборки образа.
Замени `JWT_SECRET_KEY` из примера отдельным случайным секретом:

```bash
python -c 'import secrets; import sys; sys.stdout.write(secrets.token_urlsafe(48) + "\n")'
```

Сначала собери образ, запусти БД и примени миграции отдельным контейнером:

```bash
docker compose build app storage
docker compose up -d --wait db storage
docker compose run --rm migrate
docker compose run --rm storage-init
docker compose up -d --no-build --wait app
```

По умолчанию API доступен на `http://localhost:8000`:

- Swagger UI: `/api/v1/docs`;
- OpenAPI: `/api/v1/openapi.json`;
- liveness: `/api/v1/health/live`, возвращает `200`, пока процесс обслуживает HTTP;
- readiness: `/api/v1/health/ready`, выполняет `SELECT 1`, возвращает `200` или `503`.
- версия сборки: `/api/v1/health/version`, возвращает `release_id`.

```bash
curl --fail http://localhost:8000/api/v1/health/ready
docker compose logs -f app
docker compose down
```

PostgreSQL и MinIO хранят данные в именованных volumes; обычный `docker compose down`
сохраняет его. Порт БД не публикуется на хост. Приложение работает от отдельного
непривилегированного пользователя и пишет JSON-логи в stdout.

Для релиза задай `APP_IMAGE` с уникальным тегом, один раз собери и опубликуй образ.
Перед запуском новой версии примени её миграции через `docker compose run --rm migrate`.
Запуск подготовленного образа: `docker compose up --no-build --wait`. Конфигурация
передаётся при запуске; порт HTTP задаёт `PORT`. Смена БД выполняется через
`DATABASE_URL`, без изменения кода.

## Запуск без Docker и проверки

Нужен доступный PostgreSQL. Для запуска с хоста укажи его адрес в `DATABASE_URL`:
имя `db` предназначено для сети compose. Настройки читаются из `.env`, переменные
окружения имеют приоритет. `DATABASE_URL` обязателен и использует драйвер
`postgresql+asyncpg`.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
alembic upgrade head
python -m APP
```

Для установки только зависимостей приложения используй `requirements.txt`.
Оба манифеста фиксируют версии прямых и транзитивных зависимостей.

```bash
python -m pytest -q
```

Проверка реального PostgreSQL запускается, если в окружении задан
`TEST_DATABASE_URL`. Без него интеграционная проверка пропускается; остальные
тесты проверяют схемы, конфигурацию, HTTP-ответы, таймауты, JSON-логи и освобождение
ресурсов. Приложение запускается и при недоступной БД, но readiness возвращает
`503`, пока соединение не восстановлено.

Интеграционные тесты создают отдельные схемы со случайными именами и удаляют их
после проверки. Пользователю тестовой БД нужно право `CREATE` на базу. Тесты
проверяют миграции, ограничения каталога, конкурентные запросы авторизации и
отзыв сессий. Для проверки согласованности моделей и миграций:

```bash
alembic check
```

## Каталог и миграции

Модели: `City`, `Genre`, `User`, `Artist`, `Album`, `Track`, `Venue`,
`AuthSession`, `EventLog`, `Rating`, `Review`, `Favorite`, `Playlist`,
`PlaylistTrack`, `Media`, `Event`, `EventType` и `Follow`. Связи жанров и артистов хранятся в отдельных таблицах.
У `track_artists` и `artist_members` роль входит в состав первичного ключа:
один участник может иметь несколько ролей. `Artist.user_id` допускает `NULL`;
удаление пользователя сохраняет артиста без владельца. У альбомов и треков
`user_id` хранит загрузившего пользователя и также может быть `NULL` для импорта.

Агрегаты оценок хранятся у треков, альбомов, артистов и площадок. PostgreSQL
проверяет допустимые координаты, положительную длительность и вес пользователя,
согласованность агрегатов, роли и уникальность связей. Email уникален без учёта
регистра; города уникальны по имени, региону и стране, включая отсутствие региона.

Alembic использует ту же конфигурацию и asyncpg. `alembic upgrade head` разворачивает
схему с нуля. HTTP-процесс не запускает миграции и не создаёт таблицы автоматически.
Для новой миграции после изменения моделей:

```bash
alembic revision --autogenerate -m "describe_change"
```

Сгенерированный файл нужно проверить перед применением; значения в миграциях
фиксируются независимо от текущих констант моделей.

## Работающий каталог

Для `/api/v1/artists`, `/api/v1/albums` и `/api/v1/tracks` доступны:
`POST` для создания, `GET` для списка, `GET /{id}` для деталей и `PATCH /{id}`
для изменения. Чтение публичное с опциональным Bearer-токеном; создание и
изменение требуют авторизации. Владельцем становится текущий пользователь.
Нельзя передать или изменить `user_id` через API.

Минимальные тела запросов после входа:

```json
{"name": "Solo"}
```

```json
{"title": "Release", "artist_ids": [1], "release_date": "2026-01-01"}
```

```json
{
  "title": "Track",
  "duration": 120,
  "album_id": 1,
  "artist_credits": [
    {"artist_id": 1, "role": "guitar"},
    {"artist_id": 1, "role": "vocals"}
  ]
}
```

Вместо `artist_credits` трек может принимать `artist_ids`: каждому назначается
роль `primary`. Одновременно оба способа указывать нельзя. У релиза и трека
должен быть хотя бы один артист. Все привязываемые артисты должны принадлежать
текущему пользователю; для трека также проверяется владелец альбома. Совместные
релизы разных владельцев потребуют отдельного механизма согласования доступа.
Обычные участники меняют только свои сущности; moderator и admin могут редактировать общий каталог. Существующие импортированные
сущности без владельца доступны для чтения; присвоение владельца пока не реализовано.

Все три сущности принимают `genre_ids`. Список жанров доступен через
`GET /api/v1/genres`; создание - через `POST /api/v1/genres` для privileged,
с телом `{"name": "Jazz", "slug": "jazz"}`. Повторный slug возвращает `409`.
Артист также принимает `bio`, `image_url`, `city_id`; альбом - `cover_url`;
трек - `cover_url`, `lyrics`. URL принимаются только с HTTP/HTTPS.
Пропущенные поля PATCH сохраняются; явный `null` очищает nullable-поля,
а пустой `genre_ids` удаляет связи с жанрами.

Списки возвращают `{items, total, limit, offset}`. `limit` от 1 до 100,
по умолчанию 20; `offset` неотрицательный. Общие поля сортировки: `id`,
`created_at`, `ratings_count`, `rating_avg`; у артиста также `name`, у релиза и трека `title`,
у релиза `release_date`, у трека `duration`. Префикс `-` означает убывание;
по умолчанию `sort=-created_at`. `createdAt` и `releaseDate` поддерживаются
как алиасы. Одинаковые значения упорядочиваются по `id`, `NULL` идут в конце.
Неизвестное поле возвращает `422`. Альбомы фильтруются по `artist_id`,
треки - по `artist_id` и `album_id`.

В деталях артиста считаются альбомы и уникальные треки, у альбома - количество
треков и длительность. Вложенные артисты и альбомы используют `Short`.
Операции каталога и публичный `EventLog` фиксируются одной транзакцией.
SQLAlchemy-связи загружаются через `selectinload`; неявные lazy-запросы запрещены.

## Оценки

`PUT /api/v1/ratings` устанавливает или заменяет собственную оценку:

```json
{"target_type": "track", "target_id": 1, "value": 4.5}
```

`DELETE /api/v1/ratings/{target_type}/{target_id}` снимает собственную оценку.
Оба маршрута требуют Bearer-токен и возвращают `target_type`, `target_id`,
`rating_avg`, `ratings_count`, `my_rating`. Повторный DELETE существующей цели
без собственной оценки успешно возвращает актуальное состояние. Несуществующая
цель возвращает `404`. Поддерживаются `track`, `album`, `artist`, `venue`.
Оценка - число от 1 до 5 с шагом 0.5; строки и boolean отклоняются.

Публичная оценка — средняя с весами пользователей:

```text
S = Σ(value × weight)
W = Σ(weight)
rating_avg = S / W
```

Если все три пользователя поставили 5, `rating_avg=5.0` независимо от их весов.
При отсутствии оценок возвращается `null`. `ratings_count` считает пользователей,
а не сумму весов. `rating_avg` - вычисляемое поле Pydantic, суммы в API не выдаются.
Анонимный посетитель получает `my_rating=null`; для авторизованного используется
LEFT JOIN по `(user_id, target_type, target_id)` в том же запросе, что и агрегаты.
Сортировка по рейтингу использует ту же формулу; неоценённые цели идут в конце.

Веса девяти XP-уровней: `1, 1.2, 1.4, 1.7, 2, 2.3, 2.6, 3, 3.5`.
У модераторов и администраторов вес `4` независимо от XP.
При PUT вес определяется по текущему уровню и сохраняется в `Rating.weight`;
`User.weight` синхронизируется с применённым значением. Смена уровня или настройки
весов сохраняет старые оценки: новый вес применяется только при следующем PUT.
DELETE вычитает сохранённый вес. Повторный PUT с тем же value после смены уровня
применяет новый вес. Для рекомендаций отдельно считается Bayesian-показатель
`B=(S + C × M)/(W + C)`, по умолчанию `C=50`, `M=3.0`. Он учитывает объём оценок:
высокая средняя на нескольких голосах не гарантирует верх выдачи. Изменение `C`/`M`
влияет на ранжирование рекомендаций, а не на публичное `rating_avg`.
Настройки доступны через `RATING_PRIOR_STRENGTH`,
`RATING_PRIOR_MEAN`, `RATING_LEVEL_WEIGHTS` (JSON-массив девяти чисел),
`RATING_WEIGHT_MODERATOR`, `RATING_WEIGHT_ADMIN`. Все экземпляры приложения
должны использовать одну политику. Альтернатива - пересчёт исторических весов
при смене уровня; для MVP выбран сохранённый вес, чтобы такие изменения не
требовали массовой перезаписи агрегатов. Динамическая средняя по каталогу также
возможна позже; фиксированная M позволяет сравнивать результаты воспроизводимо.
Для применения новой политики к существующим оценкам предусмотрена отдельная
команда `python -m APP.recalculate_ratings`: веса и агрегаты пересчитываются
одной транзакцией, запись оценок кратковременно блокируется. Повторный запуск
не меняет уже актуальные данные. Оценки и рецензии не удаляются.

Оценка уникальна для пользователя и цели. Внутренние nullable-FK связывают
полиморфную пару с конкретной таблицей; CHECK разрешает только одну согласованную
ссылку. Веса и агрегаты используют NUMERIC. Транзакция сначала блокирует
пользователя через FOR NO KEY UPDATE, затем цель через FOR UPDATE: разные
пользователи и одновременные PUT/DELETE одной цели не теряют изменения.
Оценка, суммы, количество и публичный EventLog фиксируются вместе.
FOR NO KEY UPDATE у пользователя сохраняет совместимость с FK при создании
каталога. Прямые записи в ratings обходят пересчёт агрегатов, поэтому изменения
оценок должны проходить через сервис. Удаление аккаунта с оценками ограничено FK:
будущая операция удаления должна сначала снять его оценки и обновить суммы.
Удаление самой цели каскадно удаляет относящиеся к ней оценки.

Миграция `0003_ratings` добавляет таблицу оценок и переводит веса/агрегаты в NUMERIC.
Применяется отдельным процессом перед запуском новой версии приложения.

## Авторизация и права

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/auth/register` | Создать аккаунт, вернуть `UserMe`; не выполнять автоматический вход |
| `POST /api/v1/auth/login` | Получить access- и refresh-токены |
| `POST /api/v1/auth/refresh` | Обменять refresh-токен на новую пару |
| `POST /api/v1/auth/logout` | Отозвать текущую сессию, вернуть `204` |
| `GET /api/v1/me` | Получить собственный профиль с email и level |
| `GET /api/v1/me/artists` | Список собственных артистов |
| `GET /api/v1/me/albums` | Список собственных альбомов |
| `GET /api/v1/me/tracks` | Список собственных треков |
| `GET /api/v1/users/{user_id}` | Получить публичный профиль без email и level |

Списки студии `/me/artists`, `/me/albums`, `/me/tracks` требуют Bearer-access
и возвращают `Page` с `items`, `total`, `limit`, `offset`. Фильтр владельца
применяется к странице и общему количеству по текущему пользователю;
администратор также получает только свои записи. Параметры `limit`, `offset`
и разрешённый `sort` работают так же, как у публичного каталога.
Результаты содержат личную оценку и лайк; ответы имеют `Cache-Control: no-store`.
Публичные списки сохраняют прежнее поведение. Изменение не требует миграций.

Регистрация принимает JSON:

```json
{"email": "listener@example.com", "password": "long-listener-password", "display_name": "Listener"}
```

Вход принимает `email` и `password`. Ответ содержит `access_token`, `refresh_token`,
`token_type="bearer"`, `expires_in` и `refresh_expires_in` в секундах. На защищённых
маршрутах передавай `Authorization: Bearer <access_token>`. В Swagger вставь access
в поле Authorize. Refresh принимает JSON `{"refresh_token": "<refresh_token>"}`.
Logout требует действующий access-токен; если он истёк, сначала выполни refresh.

Access - JWT HS256, по умолчанию на 15 минут. Refresh - случайный непрозрачный
токен; в PostgreSQL хранится только SHA-256 хеш. Сессия действует 30 дней с момента
входа: ротация не продлевает этот срок. При refresh прежний refresh становится
недействительным; конкурентный обмен одного токена успешно выполняется только
один раз. Access ограничен оставшимся сроком сессии. До logout уже выданные access
работают до своего срока; logout немедленно отзывает все access и refresh текущей
сессии. Сессии других устройств сохраняются. Сроки, issuer, audience, секрет и
стоимость хеширования задаются через env.

Пароли хешируются passlib `bcrypt_sha256`, чтобы длинные UTF-8 пароли не усекались
на границе bcrypt. Версия bcrypt закреплена для совместимости с passlib. Хеширование
выполняется в thread pool. Регистрация всегда выдаёт уровень `green`; клиент не
может передать level, weight или is_active.

`level`: `green / experienced / moderator / admin` - источник прав.
`type`: `user / artist` - творческая роль, вычисляемая по владению хотя бы одним
`Artist`. Пользователь может быть одновременно артистом и модератором. `weight`
хранится отдельно; политика применения и сохранения весов описана в разделе оценок.

Зависимости находятся в `APP/core/dependencies.py`: обязательная и опциональная
авторизация, privileged и admin. Проверки владельца - `require_owner` и
`require_owner_or_privileged`. В write-операции нужно загрузить ресурс, проверить
его существование и владельца, затем изменить данные и записать `EventLog` в
одной транзакции. `require_owner` не предоставляет неявный обход администратору;
для операции с доступом владельца или privileged используй второй helper.

Авторизация использует отдельную короткую read-сессию, поэтому операция сервиса
может начать собственную транзакцию. Уровень и активность пользователя проверяются
по БД при запросе. На публичном маршруте отсутствие токена разрешено, а переданный
недействительный токен возвращает `401`. Недостаток прав возвращает `403`.

Регистрация, вход, refresh и logout записывают непубличные `EventLog` в одной
транзакции с изменением данных. Эти события не содержат пароли, email или токены;
публичная лента должна выбирать только `is_public=true`.

## Соглашения схем

`Short` содержит поля вложенной карточки; `RatedShort` добавляет `rating_avg`,
`ratings_count`, `my_rating`; `Out` расширяет `RatedShort` деталями. Треки
плейлиста выдаются отдельным эндпоинтом как `PlaylistTrackItem` с
`TrackRatedShort`. `PlaylistOut` не содержит список треков.

Входные схемы отклоняют неизвестные поля, пустые названия и неположительные ID.
Для PATCH используй `model_dump(exclude_unset=True)`: отсутствие поля сохраняет
значение, явный `null` очищает только nullable-поля. Даты событий принимаются с
часовым поясом. При обновлении одной даты сервис должен сравнить её со второй
датой, сохранённой в БД.

AsyncSession выдаётся через `SessionDependency`. Сервис задаёт транзакцию,
например `async with session.begin()`. Dependency закрывает сессию, но не
выполняет автоматический commit. Движок создаётся в lifespan и освобождает пул
при завершении приложения.

контекст проекта и реализованные схемы.

Какая схема на деле:

https://habr.com/ru/articles/1005390/?ysclid=muggko1ykp177623640

В идеале схема должна будет быть такая:

# есть root где находится главный интерфейс приложения

## Рецензии и библиотека

Одна рецензия пользователя на цель. `POST /api/v1/reviews` принимает
`target_type`, `target_id`, `title` и `text`; оценка должна уже существовать.
Значение `rating` читается из `Rating` при каждой выдаче. Замена оценки обновляет
отображаемое значение. Удаление оценки каскадно удаляет рецензию и её лайки;
удаление самой рецензии оставляет оценку. Чтение публичное, изменение - владельцем, moderator или admin.
`GET /reviews` поддерживает пагинацию и фильтры `target_type`, `target_id`.

Лайки: `PUT /api/v1/favorites` с `{ "entity_type": "track", "entity_id": 1 }`;
отмена - `DELETE /api/v1/favorites/track/1`. Повторные запросы идемпотентны.
Поддержаны треки, альбомы, артисты, площадки, события, рецензии и плейлисты.
`GET /api/v1/me/favorites` возвращает библиотеку с пагинацией и фильтром
`entity_type`. Поля `likes_count`, `is_liked_by_me` заполняются из этой таблицы.

У каждого аккаунта есть приватный системный плейлист `kind=liked`.
`Favorite` - единственный источник его треков: сначала последние лайки,
при равном времени - больший ID. В `playlist_tracks` эти треки не дублируются.
Переименование, удаление, изменение порядка, обложки или добавление треков
через маршруты обычных плейлистов запрещены.

Обычные плейлисты создаются через `POST /api/v1/playlists` и по умолчанию приватны.
`GET /api/v1/me/playlists` - свои, включая Liked; `/me/saved-playlists` -
сохранённые чужие публичные. Сохранение использует лайк плейлиста. Приватная
подборка доступна владельцу; сторонний посетитель получает `404`.
При переводе сохранённой подборки в приватную она скрывается у остальных.

`PlaylistOut` содержит сведения о подборке, а треки выдаются отдельно:
`GET /api/v1/playlists/{id}/tracks?limit=20&offset=0` возвращает элементы
`{track, position, added_at}`. Добавление: `POST` того же пути с
`{ "track_id": 1, "position": 0 }`, где позиция необязательна; удаление:
`DELETE /playlists/{id}/tracks/{track_id}`. Перестановка:
`PUT /playlists/{id}/tracks/order` с `{ "track_ids": [3, 1, 2] }`;
нужна полная перестановка текущих треков без повторов. Позиции начинаются с нуля,
дубликаты трека запрещены, максимум - 10 000 треков. Блокировка плейлиста
сериализует конкурентные изменения; уникальность позиций проверяется при commit.

## Файлы, S3 и воспроизведение

`POST /api/v1/media/images` и `/media/audio` принимают multipart-поле `file`
и возвращают ID файла, формат, размер, SHA-256 и метаданные. Нужна авторизация.
JPEG/PNG/WebP ограничены 10 МиБ и 25 млн пикселей; анимация не принимается.
MP3/FLAC/WAV ограничены 100 МиБ. Заголовок Content-Type не считается доказательством
формата: Pillow проверяет изображение, Mutagen - структуру и длительность аудио.
Пределы настраиваются через env; слишком большой файл или HTTP-body получает `413`.
Временный файл удаляется после обработки запроса.

Загруженный файл принадлежит пользователю. `PUT /api/v1/images/{target_type}/{id}`
с `{ "media_id": 1 }` прикрепляет изображение к `user`, `artist`, `album`,
`track`, `venue` или `playlist`. `PUT /api/v1/tracks/{id}/audio` прикрепляет аудио
и устанавливает длительность трека из файла. Нужны права редактирования цели и владение загруженным файлом.
Файл другой разновидности получает `422`. У артиста используется `image_url`,
у пользователя - `avatar_url`, у остальных - `cover_url`.

В PostgreSQL хранятся ключ и метаданные, в S3 - содержимое. URL обложки ведёт
на `/api/v1/media/{id}/content`: после проверки текущего доступа API перенаправляет
на временную подписанную ссылку. Неприкреплённый файл доступен только владельцу;
файл приватного плейлиста скрыт от остальных. `GET /media/{id}` возвращает
метаданные владельцу. Публичный файл может быть доступен через несколько целей.

Для проигрывателя: `GET /api/v1/tracks/{id}/playback` возвращает
`url`, `expires_in`, `content_type`, `duration`; `/tracks/{id}/audio` перенаправляет
на файл. S3 обслуживает частичные запросы `Range`, API не буферизует аудио.
Срок ссылки задаёт `S3_PRESIGN_TTL_SECONDS`, по умолчанию 300 секунд. Уже выданная
ссылка действует до истечения этого срока, даже если плейлист стал приватным.
При замене обложки внешним URL старая связь с загруженным файлом снимается.

`S3_ENDPOINT_URL` - внутренний адрес для записи, `S3_PUBLIC_ENDPOINT_URL` - адрес,
доступный браузеру; подпись создаётся сразу для внешнего адреса. Подменять hostname
в готовой ссылке нельзя. `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET`, `S3_REGION`
и таймауты передаются через env. Без конфигурации S3 файловые операции возвращают
`503`, остальные функции работают. При запуске с хоста замени `storage` в URL
на доступный адрес MinIO. Секреты MinIO и S3 в локальном примере должны совпадать.

Локальное хранилище собирается из исходников официального релиза MinIO
`RELEASE.2025-10-15T17-29-55Z`: опубликованные образы недоступны. Первая сборка
дольше из-за Go и зависимостей, дальнейшие используют Docker cache.
Исходники и лицензия: https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z.
MinIO доступен на `http://localhost:9000`, консоль - `http://localhost:9001`.
Для MinIO CORS задаёт `MINIO_CORS_ALLOW_ORIGIN` (список origins через запятую):
его S3 API не поддерживает настройку CORS отдельного bucket. Для S3 с поддержкой
этого API `storage-init` применяет `S3_CORS_ORIGINS` (JSON-массив).
Bucket создаётся отдельным процессом `docker compose run --rm storage-init`.
Файлы сохраняются в volume `minio_data`; API не использует локальный каталог медиа.

Две внешние системы не имеют общей транзакции: до записи S3 создаётся
`Media.status=pending`, после успешной записи - `ready`. При ошибке выполняется
компенсация. Незавершённая загрузка остаётся известной БД, её ключ можно убрать
одноразовым процессом `docker compose run --rm media-cleanup`; по умолчанию он
обрабатывает pending старше суток. Более короткий интервал должен превышать
максимальную продолжительность живой загрузки. Готовые файлы эта команда не удаляет.

## Площадки, события и подписки

`POST/GET/PATCH /api/v1/venues` создают и читают площадки с городом, адресом
и координатами. Площадка оценивается через существующий `/ratings` с типом `venue`.
Изменение доступно владельцу или privileged. Город добавляет privileged через
`POST /api/v1/cities`, публичный список поддерживает `q`, `limit`, `offset`.
Часовой пояс города проверяется как IANA timezone.

`POST/GET/PATCH/DELETE /api/v1/events` работают с событиями. Нужен город или
площадка; координаты по умолчанию берутся из площадки либо города и сохраняются
у события. Город площадки и события должен совпадать. Время принимается с timezone,
`stop_at` должен быть позже `starts_at`, частичные изменения проверяются также
против сохранённых дат. `venue_id=null` отвязывает площадку. `/event-types`
возвращает предзаполненные `concert`, `jam`, `find_a_group`.

Списки площадок и событий поддерживают `city_id` и полную рамку
`min_lat`, `max_lat`, `min_lng`, `max_lng`. События дополнительно фильтруются
по `starts_after`, `starts_before`, `type_event_id`; сортировка выбирается
из разрешённых полей. В MVP фильтрация по рамке, без расчёта расстояний.

Подписка: `PUT /api/v1/follows` с `{ "target_type": "artist", "target_id": 1 }`;
отмена - `DELETE /api/v1/follows/artist/1`. Типы - `user`, `artist`, `venue`.
Самоподписка запрещена, повторы не создают дубликаты. `/me/following` возвращает
свои подписки. `/me/feed` выдаёт события от подписанных пользователей и события,
связанные с подписанными артистами или площадками, с пагинацией по времени.
Счётчики и `is_followed_by_me` заполняются для профилей, артистов и площадок.

Бизнес-запись и `EventLog` входят в одну транзакцию PostgreSQL. Авторизация,
служебные операции с медиа и приватные плейлисты записываются как непубличные.
Лента дополнительно проверяет текущее существование и видимость целей, поэтому
удалённые сущности и ставшие приватными плейлисты не раскрываются через историю.

Интеграционные тесты дополнительно проверяют рецензии и их каскады, Liked,
перестановки и конкурентные изменения, ограничения БД, доступ к файлам,
компенсацию ошибок хранилища, события и приватность ленты. Для теста настоящего
S3 задай `TEST_S3_ENDPOINT_URL`, `TEST_S3_ACCESS_KEY`, `TEST_S3_SECRET_KEY`,
`TEST_S3_BUCKET` вместе с `TEST_DATABASE_URL`; bucket должен быть уже создан.

## Рекомендации

`GET /api/v1/recommendations/tracks?limit=20&offset=0` выдаёт музыку для открытия:
любимые жанры, жанры лично оценённой музыки и общий Bayesian rating формируют
итоговый балл. Без личных сигналов используется общий рейтинг. Уже оценённые,
лайкнутые и собственные треки исключаются для авторизованного посетителя.
`playable_only=true` оставляет только треки с готовым аудио.

Выбор любимых жанров: `GET /api/v1/me/favorite-genres` и `PUT` того же пути
с `{ "genre_ids": [1, 2] }`; пустой список очищает предпочтения. Ответ рекомендаций
содержит составляющие балла, причины подбора и версию алгоритма `rules_v1`.
Коэффициенты задаются через env. Формула и примеры: [docs/recommendations.md](docs/recommendations.md).

Схема:
Браузер -> localhost:8080 -> front(NGINX) -> /api/ -> Service app:8000 -> FastAPI -> db:5432
                                                                                  -> storage:9000 MinIO
Браузер -> подписанная ссылка localhost:9000 -> port-forward -> MinIO


Что здесь происходит:
- Браузер открывает сайт по адресу localhost:8080.
- port-forward направляет соединение в выбранный под frontend внутри minikube.
- Nginx отдаёт HTML, JavaScript и CSS. Запросы с путём /api/ проксирует в backend.
- Service app:8000 предоставляет постоянный внутренний адрес backend и направляет соединения к готовым подам FastAPI.
- FastAPI обрабатывает запросы: авторизацию, работу с треками, плейлистами и другими сущностями.
- PostgreSQL db:5432 хранит пользователей, названия треков, связи с авторами, плейлисты и сведения о медиа.
- MinIO storage:9000 хранит сами аудиофайлы и изображения.
Вторая схема показывает получение медиа:
Браузер → подписанная ссылка localhost:9000
                       ↓
                  port-forward
                       ↓
                     MinIO
Backend возвращает браузеру подписанную ссылку на файл с ограниченным сроком действия. Браузер обращается по ней на localhost:9000, а второй port-forward направляет запрос в MinIO.
Содержимое аудио или изображения приходит из MinIO напрямую в браузер. FastAPI выдаёт ссылку, но в этой схеме не передаёт через себя байты файла. Поэтому нужны два туннеля: 8080 для сайта и API, 9000 для медиа
