# План фронтенда

Согласованный стек: React + TypeScript + Vite. Первая цель — сценарий
«найти музыку → прослушать → оценить → написать рецензию → сохранить».
Оценки — основная кнопка и основной сигнал рекомендаций. Плеер сохраняет
состояние при переходах между страницами.

## Организация приложения

Фронтенд разместить в `frontend/` того же репозитория. Использовать React Router
для маршрутов, TanStack Query для серверных данных и простой React context
с reducer для плеера. Текущий Audio-элемент находится в общем layout и не
перемонтируется с маршрутами. Отдельный Redux, дизайн-система и SSR пока не нужны.
Обсудить SSR, если появится требование к индексированию публичного каталога.

```text
frontend/
  src/
    app/             # providers, router, общий layout
    api/             # клиент HTTP, generated типы, обработка ошибок
    components/      # карточки, оценка, формы, пагинация
    features/
      auth/
      catalog/
      player/
      ratings/
      reviews/
      library/
      recommendations/
      events/
      feed/
```

Поля, методы и локальные переменные проекта называть на английском в snake_case;
React-компоненты — в PascalCase согласно требованиям React. Поля API не
преобразовывать вручную. Backend-сущности
не дублировать вручную: генерировать типы из `/api/v1/openapi.json`, проверять
контракт в CI. Версии npm-зависимостей фиксировать в package-lock.json,
установка через `npm ci`, Node закрепить после выбора совместимых версий.

## Этапы и критерии готовности

| Этап | Что сделать | Проверяемый результат |
| --- | --- | --- |
| 1. Каркас | Vite, TypeScript, Router, QueryClient, layout, адаптивная навигация, API-клиент, общие loading/error/empty состояния | Каталог читается из реального API, ошибки 401/403/404/422 отображаются корректно |
| 2. Вход и предпочтения | Регистрация, вход, `/me`, logout, выбор любимых жанров | Пользователь входит, выбирает жанры и видит изменение рекомендаций |
| 3. Каталог | Списки и детали артистов, альбомов, треков; разрешённая сортировка, пагинация | Можно открыть трек, перейти к альбому и артистам, поделиться URL |
| 4. Плеер | Постоянный HTMLAudioElement, play/pause, seek, громкость, очередь, следующий/предыдущий трек | Переход по маршруту не останавливает музыку, seek использует Range, истёкшая ссылка обновляется |
| 5. Оценки и рецензии | Оценка 1..5 с шагом 0.5, изменение/удаление, форма рецензии, список | После оценки обновлены карточка и рекомендации; рецензия использует текущую оценку |
| 6. Библиотека | Лайки, Liked, создание/редактирование плейлиста, сохранение чужого, порядок треков | Лайк виден в Liked; приватная подборка скрыта; перестановка работает с полной очередью |
| 7. Главная с рекомендациями | Персональная или общая подборка, объяснение «почему», признак отсутствия аудио | Пользователь понимает связь между своим выбором, оценками и результатом |
| 8. Кабинет автора | Создание Artist/Album/Track, загрузка обложки и аудио, привязка media_id | Владелец публикует playable-трек; ошибки формата и лимита объяснены до и после запроса |
| 9. События и социальные экраны | Площадки, события, фильтр города и дат, подписки, лента | Работает поиск по городу и расписанию, подписка добавляет связанную активность |
| 10. Подготовка выпуска | Тесты основных сценариев, доступность, мобильные состояния, сборка и раздача SPA | Проверенный пользовательский сценарий проходит в staging и после обновления образов |

Начать с этапов 1–3 и плеера; базовую кнопку оценки включить на странице трека
сразу, когда доступен компонент оценки. После библиотеки собрать главную.
Карты, drag-and-drop и анимации можно добавить после рабочих форм и кнопок.

## Авторизация и границы API

Сейчас backend возвращает access/refresh в JSON, принимает refresh в теле запроса.
Для первого технического прототипа оба токена можно держать в памяти: после
перезагрузки страницы потребуется снова войти. Не фиксировать такое поведение
как финальный пользовательский сценарий.

До полноценного экрана авторизации добавить на backend браузерный режим refresh:
HttpOnly cookie, Secure в HTTPS-окружении, SameSite и проверку Origin/CSRF для
операций с cookie. Bearer-access держать в памяти. Обновление токена выполнять
единственным общим Promise; при нескольких вкладках согласовать ротацию.
Logout отзывает сессию на backend, удаляет cookie и очищает QueryClient.
Существующий JSON-контракт сохранить для других клиентов. Это конкретная задача
этапа 2; cookies в текущей backend-итерации ещё не реализованы.

Предпочтительная схема запуска — один origin: `/` отдаёт SPA, `/api/v1` проксируется
к FastAPI. В dev Vite proxy направляет `/api` к локальному backend. Поэтому SPA
обращается к относительному `/api/v1`, один собранный фронтенд пригоден для
dev/staging/prod. Секреты никогда не попадут в `VITE_*`: эти значения входят в
клиентскую сборку. Если требуется отдельный API origin, использовать runtime-конфиг
и разрешить точный origin через `CORS_ORIGINS`; S3 имеет отдельную настройку CORS.

## Особенности существующего backend

- Рейтинг показывать как `rating_avg`, а личную оценку — как `my_rating`.
  `null` означает отсутствие оценки. Не вычислять Bayesian average в браузере.
- Список треков плейлиста читается отдельным пагинируемым запросом.
  Системный `kind=liked` нельзя переименовать, удалить или переставлять.
- Перестановка требует всех track_ids. Для первой версии загрузить все страницы
  редактируемой подборки и предоставить кнопки вверх/вниз. При конфликте перечитать
  полный порядок; позже можно добавить API перемещения одного элемента.
- Создание рецензии требует уже выставленной оценки. Удаление оценки также удаляет
  рецензию — показать это в подтверждении удаления.
- Права контролирует backend. `is_owner` и `level` управляют доступностью кнопок,
  но не заменяют проверку 403/404.
- `GET /tracks/{id}/playback` возвращает временную ссылку. По истечении срока
  получить новую, сохранить currentTime и продолжить; избегать бесконечных retries.
- Для музыкальной очереди рекомендации запрашивать с `playable_only=true`.
  Остальные карточки доступны для оценок даже без загруженного аудио.
- Поиск текста музыки пока не реализован, хотя публичные списки и фильтры работают.
  До добавления поля поиска согласовать отдельный query `q` для каталога.
- Полноценное редактирование пользовательского профиля, refresh-cookie и счётчики
  загрузки/прогресса требуют отдельных backend-задач. Не рисовать рабочие действия,
  пока для них нет API; multipart-прогресс можно реализовать XMLHttpRequest.

## Обновление состояния и проверки

После PUT/DELETE ratings инвалидировать detail/list/recommendations и reviews;
после favorite — карточку, Liked, favorites и saved-playlists; после изменения
плейлиста — detail, tracks, библиотеку. На первом этапе дождаться успешного ответа,
затем обновлять данные; optimistic UI вводить для часто используемых операций
с явным откатом при ошибке. Персональные query keys включают user_id, logout
очищает их, чтобы сведения предыдущего аккаунта не появились у следующего.

Тесты компонентов — Vitest и Testing Library, e2e — Playwright на настоящем
backend и PostgreSQL в staging/CI. Проверить регистрацию и refresh, оценку с
шагом 0.5, каскад рецензии, Liked, приватность плейлиста, порядок, upload, seek
и переходы с продолжающейся музыкой. Все элементы управления доступны с клавиатуры,
оценка и кнопки плеера имеют понятные названия, информация не кодируется только
цветом. CI фронтенда добавляется вместе с его кодом: typecheck, тесты, build, e2e.
